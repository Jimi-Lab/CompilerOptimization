## Paper-Ready Narrative

Phasar IFDS-uninit reports use 168 in the O2-g zfp run as an uninitialized use involving `z` and `x` in `zfp_encode_block_float_2`, file `src/template/encode.c`, line 26, with source text `w -= z; z -= y;`. The reported file/line pair is syntactically valid, but the source text is inconsistent: `src/template/encode.c:26` is only `}`. The reported source text recovers exactly to `src/template/revencode.c:26`, inside the reversible forward lifting transform.

The O2-g IR anchor in the disassembled artifact is `%264 = sub i32 %262, %263`. In the local `.ll` it carries `!dbg !12191`, where `!12191 = !DILocation(line: 26, column: 13, scope: !12177, inlinedAt: !12185)`. The scope `!12177` is `rev_fwd_lift_int32`, and its file is `Target/zfp/src/template/revencode.c`. This explains the line and source text in the report.

The drifted file field is explained by the same `%264` SSA value having multiple debug uses after optimization and inlining. Near the lifted arithmetic it is recorded as the `revencode.c` local `z`; later in the same optimized function it is also recorded by `llvm.dbg.value` as local variable `x` in the inline helper `int2uint_int32`, whose file is `Target/zfp/src/template/encode.c`. Phasar's `getFilePathFromIR` prefers an associated `DILocalVariable` file when an instruction is used by debug metadata, and `getDbgVarIntrinsic()` returns only one metadata user. As a result, the report combines the instruction's `DILocation` line/source from `revencode.c:26` with a variable-file attribution from `encode.c`.

This is a high-confidence `FP-LocationDrift` / source-mapping failure case triggered by optimized inline debug metadata. It should be used as evidence of report-layer fragility in O2-g IR tools, not as a source-level uninitialized-use judgment. No local O0 or O2-noinline Phasar zfp run was found under `CompilerOptimization/Result/zfp/phasar`, so this case is not yet a cross-universe inline-ablation result.
